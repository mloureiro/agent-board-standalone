# Server inventory: `agent-board-local-server`

This is a read-only inventory of the `agent-board-local-server` repository, taken at HEAD `492389c` on main with a clean tree, on 2026-11-24.

The current core pin is `mloureiro/agent-board` `d2e0253`, on the branch `local-server-v2`, with seven includes. The previous pin is `b587c6a`, on the branch `local-server`, from before the board had its own login.

- `src-tauri/src/**`, `src-tauri/tests`, `src-tauri/examples`, `Cargo.lock`, `tauri.conf.json` and `.github/workflows/ci.yml`.

## Abbreviations

- Wiki folders are named by the bead suffix: `6h4` = `wiki/agent-board-local-server-6h4/`, and the same for the others.
- **Owner walk** means the owner checked by hand on their own Mac. No walk was ever done on a clean machine.
- **Proof at an old pin**: much of the 6h4 evidence was gathered at pins `a62d3ed`/`1fd25da`, before x3q. It was not re-run at `d2e0253`. Where that matters, the status says "works (old pin)".

**Status values:**

- `works`: proven by an automated test or an owner walk, and the source says which.
- `broken`: known not to work.
- `unproven`: built, but never shown working.
- `discussed-not-built`: talked about, then deferred or rejected.

**Scope column** (feeds section 2):

- `W`: wrapper-only. It belongs to the server app in any repository layout.
- `P`: it exists only because the core is a separate repository at a pin. It may disappear in one repository.
- `A`: API/core behaviour that the wrapper depends on and proves end to end. In one repository it belongs to the API part's suite.

### 5.3 What stays manual today

- The tray itself. There is no UI automation of the menu, the `!` mark or Open board.
- The enrolment window, exercised by hand.
- Quit through the menu.
- Logout and login.
- launchd relaunch after `kill -9`.
- The login item.
- The Keychain prompt behaviour after a rebuild.
- A clean-machine install.
- A UI card run through to Done.
- Exit during a backup.

Candidates for automation:

- **Menu actions.** The headless runner already accepts SIGUSR1 for a backup and stdin for enrolment. Expose every menu action the same way.
- **launchd relaunch and login item.** Run them in a scratch user session or a macOS VM in CI.
- **Card to Done.** Run it with a stub `claude` on the worker PATH.

## 7. Open questions only the owner can answer

1. **Definition of done for "usable end to end"** (bead 36q is empty). Options:
   - a) A UI card reaching Done on the owner's Mac at the current pin.
   - b) a) plus the clean-Mac AC7 walk.
   - c) a) plus automated E2E for everything in section 5 that is marked "yes".
2. **The other Mac's data at the pre-login pin b587c6a** (bead 9kd). Options:
   - a) Build and test an upgrade path into the new repository.
   - b) Document an export and reinstall.
   - c) Discard that data.
3. **Caddy parity in the new repository.** Options:
   - a) Keep the Rust proxy as the only front and drop the Caddy parity test.
   - b) Keep Caddy for hosted boards and share one header-table source between both fronts.
   - c) Keep the Docker parity test as it is.
4. **The board's own login behind the local server.** The proxy drops Set-Cookie and the SAML 303, so only `NO_LOGIN_USER` works locally. Options:
   - a) Keep no-login on loopback.
   - b) Make the server app support the login mode (needs TLS on loopback, because production refuses a non-https `PUBLIC_URL`).
5. **Database for the API part.** Options:
   - a) Keep PGlite as a driver chosen at start, with Postgres for remote.
   - b) PGlite as a separate optional module loaded on demand.
   - c) Bundled Postgres binaries, so that RLS runs as a real non-superuser.
6. **Worker supervision.** Options:
   - a) The server app keeps running `listen`/`watch`/`dispatch` itself, reading the recipe from the CLI's contract (the 9eq design).
   - b) The CLI's own launchd/systemd setup, with labels and a config directory per server.
7. **Platforms and distribution** (blocked today by upstream having no licence). Options:
   - a) Stay arm64 macOS, local builds only.
   - b) Plan Intel, Linux and signed or notarised releases once the licence terms are known.
8. **Keychain in automated E2E.** The enrolment smoke uses the real login Keychain and can prompt. Options:
   - a) Allow it on a dedicated CI Mac with a pre-authorised signing identity.
   - b) Add an injectable credential store for tests and keep one manual Keychain check.
